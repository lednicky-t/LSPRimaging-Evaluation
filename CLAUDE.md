## Status and scope: the rewrite exception

LSPRi was rebuilt from scratch on the `rewrite` branch, and on 2026-10-29 it replaced the original app (git tag `legacy-final`; nobody used the original, the maintainer confirmed). The rebuild was an approved exception to the root "do not rewrite the architecture" rule; the exception ended with the cut-over, so further large restructuring needs a new approval. Scope is LSPRi Evaluation only: no hardware control, and no shared infrastructure for a future acquisition app. Evidence: `docs/rewrite_feature_inventory_2026-09.md`. Structure and event design: `docs/rewrite_architecture_sketch_2026-09.md`. Read it before any structural decision this file does not cover.

#### Rules that come from these features

Extracted from the moved paragraphs; the record explains why. Each is a rule, not history.

**Parallel work and export**
- A fan-out job (export, scan, analysis step 1, Feature map) takes its worker count from `lspr_core.perf` (`get_runtime().begin(...)`); the default is **Standard** (every core but one). **A tuned job must write / find identical results at any worker count** (hash test: `tests/integration/test_lspri_export_workers.py`); never tune what is saved. A new fan-out follows `docs/performance_tuning.md` (repo root). Saved counts live in `perf_profile.json` (`perf_setup.py`, installed in `main()` only, so tests never touch it).
- The fast libtiff TIFF decoder (`plane_reader.py`) is on for every thread and verified against tifffile at run time; `LSPR_TIFF_DECODER=tifffile` switches it off.

**Mask Scan, Auto mask, Feature map**
- A scan or an Auto mask run belongs to the dataset, session and mask it started with (lifecycle rules in the audit `docs/transient_scan_automask_slider_audit_2026-10-17.md`).
- Mask pointers (`MaskPointersModule`) are cosmetic and never a mask. Auto mask turns the standing pointers into individual masks as **one undo step**. Only what sits on the image border and goes nowhere is an `artefact` (never masked); a particle that arrives and rests is masked.
- The Feature map (`image_tools/mask/feature_map.py`, task `panels/feature_map_task.py`) uses **no ROIs** (it finds the disks in the picture) and never looks at the mask: moving ROIs keeps its result; a new rotation / crop or chromatic model drops it. It averages cubes before looking and reads them without background flattening (that may use the ROIs). `prepare` (slow, worker processes) and `score` (limits, ~2 s) are separate: keep the limits out of `prepare` (`stage_a_key`). Faint dirt (soft shadows of out-of-focus dust) is found but not masked by default. Masking features did not raise SNR on the bulk-step data (`docs/roi_feature_detection_2026-10-29.md`). **The kinds and the margin are not search settings** (2026-11-05): they live on the ribbon row and act on a finished result at once (`FeatureMapTask.set_kinds` / `set_margin`; the result keeps each kind's ungrown mask; the margin is regrown on a thread, never on the GUI thread; the selection the run made follows them while it is untouched, 2026-11-23). Keep new "what to add" controls out of `prepare` and `score`, and a search setting out of the ribbon row (section 12 of the same doc).

**Scan (analysis step 1) and what it stores**
- **Bump `SCAN_ALGORITHM_VERSION` when a change can alter a stored number.**
- A change to what a cell depends on must keep "same hash => same numbers" (pinned on the numbers by `tests/unit/test_lspri_scan_local_mask_keys.py`). A new thing that makes one ROI's pixels depend on another ROI must be added to `frame_reduce.local_roi_keys`, and so to `ring_reach_matrix` (shared with `frame_reduce.build_subset_layout`). The cell hash falls back to the whole layout / whole mask when background removal uses the ROIs or masks in its estimate (`masks_are_global`), when there is no mask resolver, and for free-form ROIs.
- **Sample / reference ROIs (2026-11-18; plan `docs/roi_shapes_and_linking_plan_2026-11-18.md`).** A reference ROI is scanned as one region (its pixels in the `SAMPLE` column, no ring, it loses the pixels of every sample ROI); which reference a sample is measured against is decided **afterwards on the stored numbers** (`analysis/reference_pairing.py`: linked references pooled by pixel, else the ring, else none), so a link or unlink makes nothing stale and needs no scan. **`ScanResultsModule.stored()` is the paired scan** (one row per sample ROI, reference ROIs have no row; with no reference ROI and no link it is the file's own object); the raw file is `_stored`, used by the staleness check only. The role is in the cell hash only for a reference ROI, so an all-sample session never rescans. **A list of ROIs that goes into a calculation (Spectra, Sensorgram, step table, groups, Signal map, S_bulk) is made with `RoiToolbox.sample_ids(ids)`**; a new consumer does the same. ROI position tuning never moves a reference ROI and refuses a sample that has links (it would score it against its moving ring; link-aware scoring is open, plan 1.2d); a linked reference never moves with its sample, only the built-in border does.
- **ROI shapes and borders (2026-11-18; plan `docs/roi_shapes_and_linking_plan_2026-11-18.md`, "2 Shapes").** A ROI has `AreaRoi.shape` (`domain/roi_shapes.py`: `Circle` / `Rectangle` / `MaskShape`) and `AreaRoi.border` (`Border(gap, thickness)` = the pixels g .. g + t from the shape's edge; `None` follows `AreaRoiDetectionSettings.default_border()`, `NO_BORDER` has none). There are no loose diameter / geometry-type / mask fields any more: ask the shape (`reach_radius` / `nominal_diameter` when only a size is needed). **A circle's ring radii are computed in one place, `roi_shapes.ring_radii`**: the cell hash holds them as float64 bytes, so a one-ulp difference makes a cell stale without moving a pixel. Circle pixels, numbers and radii are pinned bit for bit against the code from before the change by `tests/unit/test_lspri_scan_circle_golden.py` (only its `golden_rois()` may change; a moved pin needs the maintainer). Rectangles and masks are found inside their own box (`roi/rasterize.py` `_region_hits`; the scan and the drawing use the same function) and take part in the neighbour test with their **reach** (`RoiSet.sample_r` / `ring_out_r` hold a reach, not a radius, for them: `roi_shapes.reach_radius`, `border_reach_radius`; plan step 2.2). Property tests in `tests/unit/test_lspri_roi_shape_reach.py` pin that no pixel falls outside a window box, read box or neighbour answer; a change to a shape's pixels or reach must keep them green. The toolbox's diameter commands (`resize_rois`, `reset_roi_diameters`, `refine_rois`, `place_array`) keep a diameter API for circles and refuse other shapes; **a change of the sample diameter alone carries the ring with it** (maintainer, 2026-11-18). A rotate / flip / crop turns a rectangle's angle (`remap_rectangle`). **A pixel mask is its pixels, not its centre** (the centre is only the label point): it is drawn and hit-tested from its pixels through the frame's affine (`shape_paths_item.placed`, `shape_hits`), and **it moves by whole pixels** (2026-11-19; `RoiToolbox._at_position`, the one rule behind a drag, a typed X / Y, a wheel step, a paste: the pixels shift by `whole_pixels(asked - centre)`, the label point by exactly the same, nothing is resampled; a move under half a pixel for every ROI of the call raises "it moves by whole pixels" instead of doing nothing; a drag keeps its own whole-pixel count for the maps, `RoiGestures._map_applied`, so small mouse steps are not lost; `MaskOutlines` remembers a map's traced outline by its pixels, not its place, so a dragged map is translated, not retraced: 44 -> 3 ms on 160 blobs). Session schema 1.12; a 1.11 file is read once through `_legacy_shape_and_border` (no other migration, maintainer: the app is in development).
- **ROI / Groups table speed (2026-11-19; `docs/roi_table_performance_2026-11-19.md`, tool `tools/roi_table_timing.py`).** **Never ask the table's selection model for `selectedRows()` / `selectedIndexes()`** (they call the Python `flags()` of every cell of every selected row: 70 ms to select 160 ROIs): read `selection()` ranges (`RoiTablePanel._view_selection`) and select runs of rows (`RoiTreeModel.roi_index_runs`). A rebuild that lists the same rows in the same groups **updates in place** (`RoiTreeModel._adopt`, `dataChanged` with `VALUES_ONLY_ROLE`, no reset: groups, selection, scroll and Qt's current row stay); `RoiTablePanel._rebuild` re-applies view state only after `model.take_reset_flag()` or with `restore_view=True` (a change whose point is view state, like the Groups-only lock). One `PAINT_ROLE` answers what a ROI cell needs, not one role per fact. A speed-only change must keep the pixel hashes the timing tool prints. DEBUG stage records (one per unit of work: `roi_table.rebuild`, `.fit_step_columns`, `.step_state`, `.slow_paint`, built with `applog.StageTimer`) say where a slow rebuild spent its time: read the log with `python -m lspr_imaging_app.applog grep <file> --event roi_table.rebuild`; a new stage of the rebuild gets a `stages.mark(...)`.
- **Rim pairs, linked pairs, the Type column (2026-11-19; plan `docs/roi_shapes_and_linking_plan_2026-11-18.md`, "Rim pairs, linked pairs, the Type column").** The user's word is **rim** (labels, tool tips, messages, undo labels); the code keeps `Border` / `border` and the saved keys. **Every blob of a pixel map has a rim of its own** (`rasterize._mask_band`: the union of the bands of the 8-connected blobs, each from its own edge, minus the other blobs' pixels; a one-blob map is unchanged; a many-blob map with a rim adds `|blob-rims` to its cell hash, so only it goes stale). `RoiToolbox.rims_to_references(ids, image_shape)` turns a sample's rim into a linked pixel-map reference (a frozen copy at the reference wavelength; the rim is taken where the sample is on the cube on screen (`cube=`: a drag on a later cube is a timeline change, not the base position), and the sample becomes a **rim-less ROI**, no dormant rim next to its reference: `turn_rim_off`, on every cube, its offset and thickness kept for `add_rim`; the switch is the ROI's, not a cube's, while the rim's size follows the scope rules; identical pixels at the reference wavelength, about 3 % of the edge pixels differ under a chromatic shift), `add_rim` gives a reference or a rim-less sample a rim; both are in the right-click ROI menu. The ROI table's column 7 is **Type**: `rows.icon_of` / `kind_of` decide the pictogram (a ring only while the ROI measures against its own rim) and the colour of its kind of pair (green rim or links, amber no reference, blue reference in use, gray reference unused; `type_icons.py`; the first column's dot keeps the ROI's colour); `row.shape` stays the editing key. The table's columns 5 and 6 are the rim's offset (header `d`, from the shape's edge, negative = inside) and thickness (header `w`), the same for circle, rectangle and pixel map (`rows.COLUMN_RIM_OFFSET / COLUMN_RIM_THICKNESS`, `has_cell`, `RoiToolbox.set_rim`; they were the circle's ring diameters d_r / D_r; a ROI with no rim, e.g. a reference, has blank cells).
- Never remove the `stamped_by_previous_formula` recognition (`ScanStore.restamp`) without a migration: files from before would rescan every cube with a mask.
- The scan file's schema is `lspri_scan` 1.1 (it has the `n_masked` array the Sensorgram's mask marks read); an older scan file is replaced by a rescan.
- Finished cubes are written by `scan_store.ScanWriter` (a thread of its own), never by the thread that collects the workers' results (the pool is topped up only when that thread is back). The scan file holds plain (uncompressed) chunks; `write_batch` never writes a row outside its batch.
- `snapshot_source` runs on the GUI thread, everything else of a scan off-thread (`scan_jobs.py`). A partial read of an OME-Zarr export is bit-identical to a whole-plane read (`ScanSettings.partial_reads` switches it off). Known bottleneck, to be solved later (maintainer, 2026-10-27): the CRC32C check of every shard's index (cheaper ideas in the comment above `_SHARD_INDEX_CACHE_SHARDS` in `plane_reader.py`).
- Performance mode keeps a warm worker pool (~150 MB per idle worker); workers end by themselves when the app is gone (`scan._start_parent_watch`); a mode chosen during a scan applies after it.
- **Tools that build the app's modules (`tools/analysis_stage_timing.py` `build_modules`) must keep autosave suspended**: an edit made by a script was once saved into the real test session.

**Spectra and Sensorgram**
- **Never run a fit loop, or any long Python-heavy numpy work, in a thread next to the GUI: use a process** (it starved the GUI of the interpreter lock and froze the window: `docs/sensorgram_fit_freeze_2026-10-24.md`). The helper process falls back to the thread with a WARNING.
- Template shift: a ROI's cubes must never be split (its reference cubes are part of its trace); `fit_spectrum("template")` and a template-less `fit_and_metric` raise, so the method can never fall through to the polynomial; no baseline removal, by decision.
- Smoothing runs inside each plan step (`StatisticsSettings.smooth_within_steps`, default on, saved with the session), so a window never mixes two solutions.
- Step stats show mean ± SD of every line **as drawn**. Narrow steps get shorter text, never a smaller font: the size is the one in the size box for every selection.

- **Spectral correction rides on the display's scan object** (2026-11-20): `ScanResultsModule.stored()` returns a copy with `StoredScan.spectral` set (arrays shared), the same object until the table, the mode or the paired scan changes, so identity-keyed caches miss by themselves. `wavelength_nm` stays the nominal axis (hashes, plan matching); **a spectrum builder reads `stored.abscissa_nm()` and `passband_moments()`, never `wavelength_nm`**; a new consumer does the same, and a cache key that does not go through `trace_key` adds `stored.spectral_key()`. Nothing in `MetricSettings`. A mode with no usable table is *said* (`SpectralCorrectionModule.problem()`), never silently none. The table is read and written off the GUI thread. The correction never changes the scan, the images or any stored number.

**Experimental plan**
- The dataset's measured steps (`ImagingAcquisitionMetadata.plan`) are never written; the user's edits are an overlay in the session (`plan/`, session schema 1.5 / 1.6, block `"plan"`). An edit applies only to the step it was made on (fingerprint: number + measured start + measured note), else it is reported and left out.
- **Refractive indices**: one RI per *solution*, a step's solution is the first name of its note (`refractive_index.solution_of`). The session keeps a copy of the whole imported file with its SHA-256 (session schema 1.7, block `"refractive_index"`); a changed RIs.txt is reported, **never taken in silently**; **the imported copy is never changed: the user's edits (cells, added / removed rows, rows given to steps by hand) are a separate working table `RiTable.rows` that every calculation reads (2026-11-13, session schema 1.9, `docs/refractive_indices_2026-11-12.md` "Editing"); an edited value is flagged `SolutionRi.edited` and must be said wherever a number built from it is shown or exported (plan bar hover, S_bulk column tool tip, the export record's `ri_edits`); a new import replaces the edits only after the menu asked**; the refractometer wavelength is stamped at import from Preferences (default 589.3 nm: the lab's Rudolph Research J357 LED; 0 = "not given", never guessed for another instrument). `dataset_cleared` must reach `SessionCoordinator.unbind` before any module resets itself (`_build_modules` connects it first), or the cleared state is saved over the session.
- **A "range" is a step of the experimental plan; there is no separate ranges concept** (maintainer, 2026-10-29). A function that needs a stretch of the experiment takes a baseline step and a signal step from `ExperimentPlanModule` (`panels/step_picker.py` is the shared drop-down).
- pyqtgraph gives a right-click to the ViewBox first, so the plan bar asks first through `_MiddlePanViewBox.claim_right_click`; the bar's `shape()` needs the winding fill rule (an odd-even path makes the overlap at a shared boundary a hole).

**ROI position tuning**
- Accept copies the trial's numbers into `scan.h5` **bit-identical to a real scan of the moved ROIs** (pinned by a test): only when the trial's inputs are unchanged, only into a file that fits (`ScanStore.prepare(create=False)`), and not for ROIs next to another ROI or whose new centre is interpolated between lattice points. A trial scans the centre the toolbox stores (0.1 px rounding, `roi_tuning.moved_centre`).

**Image panel, selection tools, rails** (extracted 2026-11-25 from the moved paragraphs)
- **`panels/image/panel.py`, `roi/toolbox.py`, `app_rewrite.py` and `panels/roi_table/panel.py` are gated by size budgets** (`tests/unit/test_lspri_panel_size_budget.py`, lines and methods; raise one only on purpose, with the reason in the commit). New behaviour goes in a file of its own with a small builder (the pattern of `selection_tools.py`), not into `ImagePanel`; construction code lives in `canvas_build.py`, `ribbon_build.py`, `navigation_build.py`.
- A selection is only a selection (it limits the editing tools); the Mask tab turns it into mask pixels. Editing tools read `AreaSelectionModule.mask(shape)` (selection, else lock, else None); `selected_mask(shape)` is the selection itself. Tools compute on the whole image and are cut to the lock afterwards. **Every selection producer, the brush included, obeys the picked mode and Shift / Alt**, exactly.
- **Selection speed rules** (`docs/selection_lock_and_tool_move_2026-11-15.md` section 14): outline pens stay **width 0**; a pixel selection's outline is traced (`region_outline`), never built from rectangles and `simplified()`; polygons are filled by `rasterize_polygon`, never `skimage.draw.polygon`. Dense outlines are `CachedLineItem`s; the look is one state object, `selection_style.py`; a Subtract / Intersect result wears the Selection's look (`selection_palette.LOOK_OF`), no third row.
- **Every tool with numbers** has them in a pop-up on a right-click of its button and changes them with a right-drag on the image (`panels/image/tool_drag.py`). `create_relative_contrast_mask(side="both")` stays bit-identical to the old function.
- **The wand reads the active layer**, never a hidden one; the select-by-value tools need the Image layer active; hiding a layer never changes the active one.
- On the View rail an overlay's icon is its show / hide switch and a right-click opens the rest of its controls (`right_click_menu.py`). **A rail's pop-ups and tool tips are placed with `side_rails.beside_point` / `tooltip_point`**, never `QPoint(button.width(), 0)`. Tests that read rail geometry wait with `is_animating()`. The Histogram follows the area selection only while the View ribbon is rolled down (maintainer's choice).
- **Every code path that changes the ROI selection goes through `set_roi_selection`**, so the ROI selection lock holds (`remap_roi_ids` and `restore_roi_selection` pass it). The lock is saved in the session, not undoable.

**ROI / Groups table** (extracted 2026-11-25)
- **One `SensorgramAxis` per settings module, always made with `SensorgramAxis.of`**. `SensorgramAxis` and `StepTableModule` live in `selection/`.
- Comparison column titles are formulas with real subscripts (`step_columns.subscript_runs`), written only by `step_table_module.compare_title`, never with underscores; a step's title is the user's note and is never parsed; CSV labels stay ASCII.
- A "which rows are on screen" answer is asked again after the table's own rebuild (`RoiTablePanel._rebuild`), not only after the module's signals.
- **Frozen columns:** read `panels/roi_table/view.py`'s module docstring before touching `drawRow`, `indexAt`, `visualRect` or the delegate's column positions (they stay relative to the cell's own rectangle). A coloured step header is drawn by hand and must follow the header style sheet in `panel.py`.
- **`RoiTreeView.refresh_column_visibility` is the only code that shows or hides a column**; never call `setColumnHidden` elsewhere. Fixed widths only through `RoiTreeView.set_fixed_column_width`.

**Plots** (extracted 2026-11-25)
- **The points / lines / legend menus are one definition, `PlotLookControls` (`panels/sensorgram/plot_look.py`)**, used by every plot; the values are separate per plot (own instance, keys, defaults). Add an option there once; never copy those menus into a plot.
- **Re-ordering never draws the lines again**: an option that only moves rows (z, legend) is added to `SensorgramViewSettings.differs_only_in_order`; every other option draws again. The manual line order is the session's (`PlotLineOrderModule`).
- Sensorgram View-tab options are display only (nothing is recomputed) and remembered; they are menus of one kind (`panels/sensorgram/group_menu.py`).
- Signal-map colours are a display override (`RoiOverlay.draw(color_override=)`), no calculation of their own.

**Tests**
- Run one pytest process per test file (all files in one process stalls); offscreen Qt on Windows has no fonts, so a test that measures text width calls `tests/_qt_fonts.py` `load_system_fonts()`.
- **A UI change updates its tests in the same piece of work.** The tests live in the umbrella repo (`tests/`), not here: grep `tests/` for the widget or attribute you changed (2026-11-25: four stale test files kept CI red for three days and hid new failures).


## Where the app starts

There is one app. `src/main.py` (used by `run.py` and the Suite launcher) shows the launch screen and calls `app_rewrite.main` (the console script `lspri-evaluation` calls it directly); `app_rewrite.build_main_window` wires everything. The old `gui/`, `io/dataset.py`, `processing/` (except `reference_selection`), `domain/models.py` and `app.py` are gone; `gui/`, `io/` and `processing/` still hold a few shared modules under their old names (renaming them is phase 3 of the cut-over plan). Check what is reachable with `python tools/import_reachability.py`.

## Non-negotiable invariants

These come from real incidents. Violating any of them will likely reproduce a bug that already cost investigation time. Source: `docs/rewrite_feature_inventory_2026-09.md` section 3.

- **Never let a `QThreadPool` worker touch, even indirectly via a blocking wait, an OME-Zarr read.** Root-caused to a native `STATUS_HEAP_CORRUPTION` crash. Use plain `threading.Thread` (or a small pool built on it) for anything dataset/zarr-adjacent. The one safe exception: a single-thread `QThreadPool` for HDF5-only writes that need strict ordering.
- **Never run a curve fit, or any other nonlinear computation, on the GUI thread.** This includes anything framed as a "live preview". Display code reads already-computed values; it never computes.
- **Never pool pixels across ROIs before computing sample/reference ratios.** Every ROI's reduction stays independent through the whole pipeline.
- **Always average already-fitted per-ROI values, never average raw spectra and fit once.** Nonlinear fits don't commute with averaging.
- **Cache per-ROI analysis masks at that ROI's own small bounding box, not full-image-plane size.** Full-size caching measured 8-14 GB RAM at realistic ROI counts.
- **Masks are authored and stored in raw pixel space**, forward-transformed into processed/wavelength space at each use site via Chromatic's `warp_mask()`, never the other way around.
- **Rotation resamples with Lanczos4** (2026-10-20; bilinear smoothed the pixel noise by ~28 % and moved ROI ratios by ~720 ppm). Only the slideshow preview uses bilinear while Play runs (`fast_rotation`); the frame is redrawn exactly when Play stops. Measurement and cost audit: `docs/rotated_zarr_export_interpolation_2026-10-20.md`.
- Rotation, flip, and crop are **not display-only**. When applied, they resample the actual pixel grid every downstream calculation reads. This is deliberate (detection quality over spatial-transform purity), not an oversight.

## Module boundaries

- `dataset/`: dataset load and convert; acquisition metadata.
- `image_tools/{geometry,mask,chromatic,background}/`: independent modules. Only Chromatic's `affine_for()` and `warp_mask()` are called from outside.
- `roi/`: the ROI Toolbox, one backend with several front doors (Image panel, ROI/Group table) that call the same command API. Follow `docs/roi_shapes_and_linking_plan_2026-11-18.md` (sample / reference roles and links, shapes; supersedes `docs/roi_system_roadmap.md`); don't re-derive an ROI model. Role / link rules: `domain/roi_links.py`; links live on the sample (`AreaRoi.reference_roi_ids`) and every command that renumbers or removes ROIs must carry them (`RoiToolbox._survivor_links`).
- `analysis/`: the scan (`scan*.py`, `frame_reduce.py`), the display queries (`query.py`, `scan_view.py`, `statistics.py`), background workers (`worker.py`), reduction math (`reduction.py`) and the reference `tasks.compute_cell`. Computes only on an explicit Scan / Fast scan.
- `selection/`: the one intentionally shared state (current cube, wavelength, ROI). Not a license to add more.
- `panels/`: display only. Read query interfaces; turn gestures into command calls; own no domain state.

**Rule:** no module reads or writes another module's internal state. Coordinate through a documented interface method or a signal.

**Import layers (checked by `lint-imports` and in CI):** a package may import only from packages below it in the order `app_rewrite` > `panels` > `selection` > `dataset` > `io` > `storage` > `analysis` > `roi` > `image_tools` > `plan` > small helpers. The full floors (no upward import is excused today) and how to fix a failure: `docs/import_layering_2026-11-02.md`. If a new import fails the check, move the thing you need down or pass it in; don't add an exception without asking.

## Communication

- Each module is a `QObject` with typed `pyqtSignal`s. No string-keyed event bus.
- Every change is one of two types. `CosmeticChange`: redraw only (color, label, grouping, display mode); never triggers recompute. `ComputationalChange`: the value may now be wrong (geometry, mask, chromatic, background, reduction method); the scan's cell hashes make the stored numbers stale (it never recomputes by itself).
- Public mutating methods use the shared `@instrumented` helper (timing and DEBUG logging to the session log).
- **Heavy work reports progress and can be cancelled.** Anything that may take more than ~1 s on realistic data (reading cubes, detection, tracking, fitting, analysis, export) must:
  - be a pure function (no Qt) taking `progress: Callable[[float, str], None] | None` (overall fraction 0..1 plus a short message) and `cancelled: Callable[[], bool] | None`; check cancellation at every progress call and stop with a `Cancelled` exception;
  - report per unit of work (image, step, ROI), never per pixel, and split the 0..1 range into stages weighted by *measured* stage times (reference implementation: `tools/chromatic_landmark_lab.py`, `StageProgress`);
  - be wrapped by its owning module, which re-emits progress as a typed signal; panels only display it (progress bar or busy indicator, plus a Cancel button) and never compute.
  - Launch screen and stage timing (2026-10-24): `launch.py` (`LaunchSplash`, `StageClock`); `src/main.py` shows the card before the heavy imports, so **`launch.py` may import only PyQt6 and `applog`**. `build_main_window` logs `app.build_stage` per step: add `stages.done(...)` after a new step that may be slow. Record: `docs/startup_gui_thread_audit_2026-10-24.md`.
  - Launch: when the last dataset is reopened, `startup_tracker.py` `StartupTracker` shows "Starting up: step N of 5: ..." in that same row until the dataset, session, first image, scan results and Spectra / Sensorgram are all settled (2026-10-24; steps in `app_rewrite._build_startup_tracker`). A new thing that loads at launch adds a `StartupStep` there.
  - App-wide indicator: `panels/task_indicator.py` `TaskIndicator`, a permanent status-bar row (spinner, progress bar, start time, elapsed/ETA, Cancel; keeps the last result until dismissed; History popup; every finished run is logged). A task joins it by emitting `task_progress(task_id, label, fraction, message)` (fraction < 0 = unknown) and `task_finished(task_id, outcome, message)` (always, once per run; outcome `completed`/`failed`/`cancelled`), then three connects in `app_rewrite.py` (report, finish, cancel). Reference: `ChromaticAutoDetect`. `analysis_progress(float)` and `export_progress(int, str)` are older ad-hoc shapes; migrate them when touched.
- Each display panel has its own ~100 ms redraw-coalescing timer. Reacting to every event immediately is not the same as reacting promptly.
- **A display panel does no work while it is hidden** (closed dock, behind a tab, window minimised): it keeps the data it is handed (cheap), skips computing and drawing, and catches up once when shown again. Use `panels/visibility_gate.py` `HiddenPanelGate` (`defer()` at every redraw entry, `set_panel_visible()` connected to the dock's `visibilityChanged` in `app_rewrite.py`). Done for the Histogram, the ROI table and the Log panel; **every new display panel (Spectra, Sensorgram, ...) must do the same.** **The same goes for work a module does only for a display** (2026-11-23): the scan's out-of-date check belongs to `ScanResultsModule`, not to a panel, and only the Spectra and Sensorgram draw its answer; it is held while both docks are hidden (`app_rewrite._wire_check_follows_displays`, `set_displays_hidden`) and runs once when one is shown. It is a hold of its own, separate from the user's Live / Paused (`set_paused`), which is never changed by it. A new display of the check's answer joins that wiring; a new module that works only for a display asks whether it should wait for one too (`docs/snapshot_source_cost_2026-11-23.md`). Measured 2026-10-14: a Histogram redraw is ~30 ms of GUI time per 1.2 MP frame. **While a ROI is being dragged a panel that rebuilds on ROI changes also waits** (`HiddenPanelGate.set_held`, fed by `ImagePanel.roi_edit_running`; 2026-11-19): a debounce timer fires at every pause of the mouse, i.e. in the middle of the drag, and the next move waited ~0.5 s behind the ROI table's rebuild. Done for the ROI table; see `docs/roi_resize_drag_cost_2026-11-19.md`.
- **Heavy numpy work of a display panel does not run on the GUI thread** (2026-10-14). Pattern: gather inputs on the GUI thread, compute on a worker, draw on the GUI thread. Histogram: `compute.redraw_counts` on an `AnalysisWorker` (newest request wins; `_on_counts_ready` draws; a result from before a clear, or that arrives while hidden, is dropped). Image panel: the value range and, for a frame with NaN pixels, the ready-made 8-bit picture come from the render thread (`panels/image/display_picture.py`, byte-identical to pyqtgraph's own and pinned by `tests/integration/test_lspri_display_picture.py`). Frames, masks and regions handed to a worker are shared, not copied: never modify them in place. A control that needs the *redrawn* result (a Y refit) must wait for the draw, not assume `_redraw()` finished.
- A handler on `cube_changed` / `wavelength_changed` / `image_rendered` runs on every slideshow step: it must be O(1) in the dataset size (no scans over all records or timings; use `DatasetModule` queries, which are indexed). Two of these cost 25 ms and 18 ms per step on a 314-cube dataset before they were found (docs build log, 2026-10-14).

## Keyboard shortcuts and mouse gestures

All in one table, `shortcuts.py` (design and the list of changes: `docs/keyboard_shortcut_registry_design_2026-10-30.md`); Help -> Keyboard shortcuts (F1) shows it. **A new key or gesture is a row there first.** A menu action gets its keys with `bind_action(action, "id")` (never `setShortcut("Ctrl+...")`); a key handler asks `matches(event, "id")` / `key_matches(key, modifiers, "id")` (never `event.key() == Qt.Key.Key_...`). Matching is exact: `Ctrl+Delete` is not `Delete`; a handler that ignores the modifiers passes `NoModifier` on purpose. A mouse gesture cannot be bound by the table: it is a text row (`keys=()`, a `gesture`), the one part nothing checks, so add its line when you add the gesture. **Esc leaves the canvas tool that is on** (2026-11-19, `panels/image/tool_escape.py`; first Esc drops what the tool is doing, the next leaves it): a new canvas tool needs nothing extra if it is an `ImageTool`; a tool with something in progress adds it to `CanvasInteraction.handle_key` (return True only when it dropped something). `tests/unit/test_lspri_shortcuts.py` fails on two bindings of one scope sharing a key, on an id used in the source but not in the table, and on a key in the table nothing uses.

## Menu icons and availability

**A context menu offers only what can be done now** (maintainer, 2026-11-19): an entry whose prerequisite is not met (no ROI selected, nothing linked, no cell picked, ...) is **left out, not greyed**, and a menu with nothing in it does not open (`docs/menu_icons_2026-11-19.md`, last section; the menu bar keeps its greyed entries). Every menu entry wears an icon, and **a command wears the same icon in every menu** (2026-11-19, `docs/menu_icons_2026-11-19.md`). A menu names what an entry does, never an icon file: `give_icon(action, "delete")` (a menu built when it pops up) or `give_persistent_icon(...)` (a menu that lives as long as the window; recoloured on a theme switch) from `panels/menu_icons.py`, whose `ICONS` table is the one place that picks the icon. A new command adds a line there; a new Tabler icon is vendored first (`packages/lspr_ui/ICONS.md`). `tests/integration/test_lspri_menu_icons.py` fails on a key that is not in the table. A right-click `QMenu(parent)` calls `deleteLater()` after `exec` (it is a child of a long-lived widget).

## Logging and diagnostics

Design record: `docs/logging_design_2026-10-14.md`. Package `applog/` (Qt-free), viewer `panels/log/` (Help -> Log Console, Ctrl+Shift+L).

- Use stdlib `logging.getLogger(__name__)`; everything is captured (ring buffer for the panel, JSON Lines file in `logs/`, console only at WARNING unless `LSPR_CONSOLE_LOG` is set).
- For anything you may later want to *analyse*, use the structured helpers: `log_event(logger, "domain.action", level, **fields)` and `with timed(logger, "domain.action", **fields) as t: ...; t.set(n=...)` (nested blocks record parent ids). Event names `domain.action`; field names carry units (`load_ms`, `wl`, `mb`).
- Levels: ERROR = failed, user should know; WARNING = recovered; INFO = user-level milestones (dataset loaded, task finished, play summary); DEBUG = per-call timings, aggregated per outer unit of work. Never log per pixel or per ROI; never pass an expensive call as a log argument.
- Heavy or slow-feeling code gets stage timing when it is written (one aggregated event per frame / cube / run), not after a complaint. `@instrumented` commands are timed automatically.
- Read a saved log without the app: `python -m lspr_imaging_app.applog summary|grep FILE.jsonl`.
- `configure_logging()` runs only in `main()`; tests never call it (and must not rely on log files).

## Remembering UI state

Every user-changeable control is remembered across restarts unless the maintainer says otherwise (stated 2026-10-05). For a checkbox, checkable button, spin box or combo box, add one line: `ui_state.bind("area/name", widget)` (`panels/ui_state.py`; the store is passed in as an optional `ui_state` argument, or `restore_ui_state(store)` on a panel). For state outside a widget use `store.get`/`store.set`. A value wired by hand (not a widget `bind`) is one row in `storage/ui_state_keys.py` (key, default, type) plus its wiring line in `app_rewrite.py`: never a new `AppSettings` field. `AppSettings` holds only app-level state (last dataset, theme, window/dock layout, layout presets) and `ui_state` itself; a settings file from before 2026-10-07 is migrated on load. Values live in `AppSettings.ui_state`, written after a short pause. State that only means something for one dataset (highlight range, manual reference frame, fixed display range) is saved together with the dataset folder and restored only for that dataset. Armed canvas tools and the area-selection mode are deliberately not restored (see `docs/rewrite_build_log_2026-09.md`, 2026-10-05).

## Analysis rules

*Principles that came from the removed engine (cut-over phase 2e, 2026-10-29); the scan's own rules are under "Rules that come from these features". They hold for the scan too: nothing computes on selection or navigation, and a changed input makes a result stale, never silently wrong.*

- A scan runs **only** on explicit user action (Scan, Fast scan, ROI tuning Accept). Selecting ROIs or changing panels must never trigger computation; display reports "not yet analyzed".
- The recompute rule is deliberately simple: any change to a cell's inputs recomputes that cell. No materiality or pixel-selection comparison.
- Formula, Fit method, and Metric settings are **never** stored or put in provenance. They are recomputed live from RAM.
- One `scan.h5` per session (`analysis/scan_store.py`), plain uncompressed chunks; the cell hash decides what is stale.
- **Fractional pixel weighting (sketch section 6a) is partly built.** The raster (`roi/rasterize.py`, `rasterize_fractional`) and weighted reductions (`analysis/reduction.py`) exist and match unweighted results when weights are equal. **Not wired yet:** `analysis/tasks.py` `compute_cell` still calls the binary `rasterize_sample`/`rasterize_reference`.

## Undo/redo

- One shared `undo.undo_manager`. Import it directly, as modules import `diagnostics_hub`.
- Each mutating command pushes one `undo.FunctionCommand` (label plus `undo()`/`redo()` closures over its own module's state). Not a deep clone of module state.
- `begin_batch(label)` / `end_batch()` merge a burst (one mouse drag) into one entry.
- **The ROI / cube selection (`SelectionModule`) is never undoable. The *area* selection (`AreaSelectionModule`: rectangle, lasso, wand, invert, deselect) is undoable since 2026-11-15** (maintainer: "implement undo for selection"; it replaced the wand's Max size guard): one step per change, restoring the whole previous state; `reset()` (rotate / flip / crop) is not a step and voids older steps (version token, skipped with a message), like `MaskModule`'s. Picking a tool is not a step.
- **Reachable from the UI** (2026-10-07): Edit -> Undo / Redo, Ctrl+Z and Ctrl+Y / Ctrl+Shift+Z, application-wide (`app_rewrite.py` `_wire_edit_menu`). `UndoManager` does nothing while a gesture batch is open.
- Wired: `RoiToolbox`, `GeometryModule`, `ChromaticModule`, `BackgroundModule`, `AreaSelectionModule`.
- **`MaskModule`**: the Mask rows' commands (maintainer OK 2026-10-16), the Auto mask batch (`set_mask_changes`, one undo step, 2026-10-17) and, since 2026-11-14, every edit (`apply_candidate`, `apply_morphology`, `paint_brush` through `_commit_edit`; maintainer: "make also painting undoable") are undoable. Loading a PNG (`set_mask_change`), clearing all masks and a session load are not, so every undo entry carries a version token and is skipped, with a message, if the mask changed after it (`image_tools/mask/module.py` docstring). A future brush stroke wraps its stamps in `undo_manager.begin_batch` / `end_batch`. Masks are stored compressed (`MaskChange`, a few KB each; `.mask` is read-only), which is what makes a batch of hundreds cheap to undo.

## Sessions

A **dataset** is raw images plus acquisition metadata, never written to. A **session** is one independently reproducible working copy of everything derived from it (ROI table, masks, settings, `analysis/scan.h5`). `storage/session_coordinator.py` knows the active session; `app_rewrite.py` wires it to the modules. Full history: the design record's Sessions section.

**Autosave never writes on the GUI thread** (2026-10-17, maintainer rule: saving has no business there). Two steps: the GUI thread reads the modules and `prepare_session` copies them into plain data (several module queries return *live* mutable objects, so this must not move to the worker); one plain `threading.Thread` runs `SessionWriter.write` (PNGs + JSON; it remembers masks already on disk, so an unchanged save is ~20 ms). `flush()` waits until the data is on disk; `set_root()` does not, so code that reads a session folder back calls `autosave.wait_until_written(root)` first. A new field in the session must go through `prepare_session`, never be read from a live module by the writer. Record: `docs/session_autosave_blocking_analysis_2026-10-17.md`.

**Loading a session never reads on the GUI thread either** (2026-10-22, maintainer's choice: open blank, fill in when ready). `SessionCoordinator.active_session_changed` -> `restore` resets the modules to blank at once and starts `SessionLoadTask` (`storage/session_load_task.py`; status-bar entry "Loading session: Loading masks n of N"); **autosave stays off for that root until the load has been applied**, and a failed or cancelled load leaves it off (a blank state must never be written over the saved one). So code that opens a dataset and then reads session state (ROIs, masks) must wait for the load: tests call `_settle()` in `tests/integration/test_lspri_rewrite_session_autosave.py`. A session with no file yet is still applied synchronously. The shared thread/signal/Cancel wrapper for tasks is `threaded_task.py` (`ThreadedTask`; scan, Auto mask, mask export and session load use it). Record: `docs/session_load_off_gui_thread_2026-10-22.md`.

## Testing rules

- Pure-computation files must import and test with **zero Qt, GUI, or dataset dependency**: `analysis/tasks.py`, `analysis/provenance.py`, `analysis/reduction.py`, `roi/rasterize.py`, `roi/detection.py`. A test of one of these that needs a `QApplication` means something is wired wrong. This is checked: contract `lspri-science-no-qt` in `.importlinter` lists the Qt-free modules (add a new pure one there; details: `docs/import_layering_2026-11-02.md`).
- A weighted reduction must match its unweighted counterpart exactly when all weights are equal.
- Root numerical-tolerance and simulated-hardware rules apply.

## Pitfalls

- **ROI coordinates are in processed image space** (after rotation, flip, crop). Mixing spaces gives silently wrong results; say which space you are in. Masks are the exception (raw space). Details: `docs/image_tools_coordinate_spaces.md`.
- **Pixel-index coordinates vs view coordinates (2026-11-18, half a pixel).** Everything stored and measured (the scan, the detectors, a ROI's stored centre = the table's X / Y, a mask's pixels, `RoiToolbox.display_positions`) is in **pixel-index** coordinates (pixel `(row, col)` is the point `(col, row)`); the canvas and the pointer are in **view** coordinates (the pixel covers `[col, col+1)`). The difference is `overlay_geometry.CELL_OFFSET` = 0.5, added once, after the affine. **Anything that draws a ROI or compares the pointer with one takes its centres from `RoiQueries.view_centers`, and a pointer position becomes a stored centre only through `RoiQueries.display_to_reference`** (a circle once sat half a pixel off the pixels it measured because it was drawn from the stored centre as it stood). A new overlay built from stored positions adds the shift itself. Record and numbers: `docs/roi_shapes_and_linking_plan_2026-11-18.md`, "Half-pixel fix".
- **Many small marks on the canvas are drawn with `drawPoints` and a cosmetic pen, never as antialiased path sub-shapes** (2026-11-18, the rectangle handles): 4,000 small antialiased squares cost 43 ms as one path, 7.5 ms as one `drawRect` each, **2.7 ms** as `drawPoints` with a square-capped cosmetic pen (`panels/image/rectangle_handles_item.py`). And never work out geometry in `boundingRect()` / `paint()`: Qt calls `boundingRect()` several times per paint, so keep the result until the data or the zoom changes. Benchmark a painting change in isolation before choosing (the first rewrite of those handles was slower than the code it replaced).
- **`image_tools_enabled` must not be persisted as off.** It is turned off while the crop/rotate tool is active so the full image shows. If persisted, crops silently fail to re-apply on reload.
- **Fixed-width Qt text fields:** measure the rendered margin, not `.text()` or `.width()` alone. `field.width() - QFontMetrics(font).horizontalAdvance(worst_case_text)` near zero means clipping risk; add a few explicit pixels. Size once for worst-case content. Example: `panels/histogram/highlight_range_controls.py`. History: build log 2026-09-29/30.

## What NOT to do without checking in again first

- Don't add back the materiality or pixel-selection recompute optimization. If it becomes a measured problem, bring a proposal with a before/after measurement.
- Don't switch the analysis store back to per-settings-version files.
- Don't run analysis on ROI selection, panel navigation, or anything other than an explicit Scan.
- Don't put ROI or group business logic in a panel or view. Panels call the Toolbox command API and hold no copy of ROI or group state.
- Don't use `QThreadPool` for anything touching the dataset/zarr layer, even indirectly.
- Don't design shared infrastructure for a future acquisition app.
- Don't make a new session copy a prior session's settings or ROIs. New sessions start blank (maintainer decision, 2026-09-26). **One approved exception (2026-10-22):** the OME-Zarr export's Session button carries the session into the exported dataset (`storage/session_carry.py`, `docs/session_carry_export_2026-10-22.md`): a user-started derivation, written once into the exported dataset's own `sessions/` folder, with `derived_from.json` recording the source. There is still no duplicate / clone command.
- Don't build session rename, duplicate, or delete, or an importer for the former app's pre-existing `analysis/roi_table.json`, `measurement_backup.h5`, or `processing_profile.json`.
- Don't make loading or clearing masks undoable without checking in.
