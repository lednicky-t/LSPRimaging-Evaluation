# Step columns and comparison columns in the ROI / Groups table (2026-11-05)

**Request (maintainer).** Show, in the ROI / Groups table, one column per experiment step with the numbers the Sensorgram shows for it (mean, SD or both), for every ROI and group; sort the groups by those values; export the table. Step 2 (not built yet): math columns over the evaluation steps (S - B ...), each with an operation picker in its header, sortable too.

Answers given 2026-11-05: controls in the table's icon row after a `|` separator, no ribbon; "both" is one cell `mean ± SD`; a refresh button calculates the rows on screen (collapsed rows are skipped) and the fits are kept in a cache shared with the Sensorgram; the Subtract switch is the Sensorgram's; sorting as proposed; numbers that are out of date are dimmed and the refresh button changes; steps merged or added change the columns.

## What was built

```
 TraceStore (analysis/trace_store.py)  <-- shared: fitted metric traces + the helper process
 SensorgramAxis (selection/sensorgram_axis.py)  <-- shared: x per cube, baseline window, Subtract switch
        |                      |
   SensorgramPanel      StepTableModule (selection/step_table_module.py)
                               |   uses step_table.py (pure) -> scan_trace.build_series
                               v
                        RoiTablePanel / RoiTreeModel / delegate (panels/roi_table)
```

- **`step_table.py`** (pure). `compute_step_numbers` runs every row through `scan_trace.build_series`, the code that makes the Sensorgram's lines, and takes the `step_values` each line carries. A ROI row = the Sensorgram's "Individual" line; a group row = its "Average by group" line (all member ROIs, the Centre setting). The SD is therefore the temporal SD of the line over the step's cubes, as on the Sensorgram, **not** the spread between a group's ROIs (that is `step_stats.group_statistics`; not used here). `numbers_key` normalises the settings that cannot change a number (the Sensorgram's display mode and band) so switching them does not dim the table.
- **`TraceStore`.** The cache that was a private dict in the Sensorgram panel, plus the `TracePool`. One current key (`scan_trace.trace_key`); `known(key)` drops the old traces on a new key, `add(key, ...)` ignores a late result for an old key; emptied by `results_changed`. The app makes one and passes it to both; a Sensorgram built without one (tests) makes and shuts down its own. Two clients may fit the same missing ROI at once (duplicate work, equal results); no in-flight list on purpose.
- **`SensorgramAxis`.** The x axis, the baseline window (snapped to data points; carried to the new unit when Cube/Time is switched) and the Subtract switch, moved out of `panels/sensorgram/panel.py` unchanged (step 2 of `sensorgram_panel_split_2026-10-26.md`; `snap_to_grid` / `snap_window` moved with them and stay importable from `plot.py`). The table needs exactly the Sensorgram's x because the baseline window is in x units.
  **One axis per settings module** (`SensorgramAxis.of`, a child of `AnalysisSettingsModule`): the axis *rewrites* the baseline window when Cube/Time is switched, so two instances would each move it (found by `test_the_baseline_window_keeps_its_cubes_when_the_x_axis_unit_is_switched` the first time two existed: the second moved the already-moved window). The app, the Sensorgram and the ROI table all ask for it with `of`.
- **`StepTableModule`.** Owns the columns (`StepColumn`: ref, order, title by the plan bar's label rule, tooltip), the numbers of each row with a **stamp** of what they were computed from (scan generation, ROI renumbering epoch, fit/metric key, the steps' boundaries, Cube/Time, the statistics that matter, a group's members), `cell()` lookups that say whether a number is current, and `recalculate(rois, groups)` on a worker thread (fits in the helper process; progress as signals; newest request wins; finished fits are kept). The panel's `PanelTask` shows it in the status bar with Cancel.
- **`roi_table/step_controls.py`** (`StepColumnControls`). The buttons after the toolbar's separator, showing/hiding the columns, which rows are on screen, the refresh button's state, the export and the remembered state, split out of `panel.py` so the panel stayed at ~1,140 lines (it reached 1,376 before the split). It reaches the panel only through `StepHost`.
- **Table.** Step columns come after the fixed ones in `RoiTreeModel` (column `COLUMN_COUNT + i`); a group header is one spanned cell, so the delegate paints its numbers over the spanned cell at the columns' places (and answers their tooltips in `helpEvent`); the group name stops where the step numbers begin. Out-of-date numbers are drawn in the dim text colour. A step header sorts: groups by their value, ROIs inside a group by theirs (`rows.StepSort`, `build_sections`); a row without a number is last in either direction; "Ungrouped" stays last; the move-group buttons are off meanwhile (same rule as the Label sort). All step columns share one width (remembered).
- **Export.** `PlotExportButton` got a data-only mode (`plot_item=None`); `export_tables.roi_step_table` writes group and ROI rows in table order with mean / sd / n per step as displayed, an `up_to_date` column, notes for out-of-date rows and for the scan's own stale cubes, and a JSON record with the settings.
- **Titles.** `SensorgramPanel.plan_bar_settings()` / `plan_bar_settings_changed`; `app_rewrite._follow_step_titles` hands the text mode and separators to the module.

## Decisions I took without asking (say if you want them otherwise)

1. A group row averages **all** its member ROIs, expanded or not; the Sensorgram averages only the *selected* members. So a collapsed group is still fitted completely (the fits are the cost, and they are cached); only the ROIs of a collapsed group get no row of their own.
2. The **Ungrouped** header gets a number too (the average of the ROIs in no group), as the Sensorgram's by-group mode draws it.
3. Switching the step columns **on** calculates the rows on screen at once if they have no numbers (turning them on is asking to see numbers). Nothing is calculated at start-up, and nothing ever by itself after that: a changed input only dims the numbers.
4. A new scan file keeps the numbers (dimmed); another dataset drops them; a ROI renumbering marks every row out of date (the scan file still holds the old ids until it is run again, as the Sensorgram shows).
5. The scan's own out-of-date cubes (grey diamonds on the Sensorgram) are **not** a reason to dim: a recalculation cannot fix them. They are in the refresh button's tool tip and in the export notes.
6. Sorting by a step is not remembered across launches (its numbers are not either).
7. The Live/Paused switch is ignored: a calculation is the user's own request.
8. Step controls other than the columns button are hidden while the columns are off.

## Verified

`tests/unit/test_lspri_step_table.py` (the numbers equal the Sensorgram's lines, either Centre, order-independent), `tests/unit/test_lspri_roi_table_step_columns.py` (sorting, cell text, export table, trace store), `tests/integration/test_lspri_step_table.py` (module and panel on a real scan: shared fits both ways, out-of-date handling, Subtract shared with the Sensorgram's button, columns follow merged/removed steps and the title style, remembered state, export). The Sensorgram's own tests were re-run after the cache and axis moved (see the build log in the commit).

**Measured** (160 ROIs in 10 groups, 14 steps, fake numbers, offscreen, `scratchpad/bench_model.py`): switching the columns on or sorting by a step rebuilds the model in 12 ms; `data()` for all 2,380 step cells takes 109 ms (46 µs a cell; a viewport shows about 400 cells, so a full repaint is about 20 ms). Not tuned.

**Not looked at on screen** (GUI rule): the toolbar order and separator, the dimmed colour, the group-header numbers' alignment with the columns, the refresh button's lit colour, the column widths.

## Step 2 - built: comparison (math) columns

Answers given 2026-11-05: "just signal comparisons, S - B, maybe also with noise"; later a pick for any S and B (S1-B1, S2-B1, S1-B2 ...); an icon to add another comparison column; the operation chosen in the column's title bar; sortable. The maintainer then said "yes, continue" to my two open choices, which are therefore what is built:

- **Difference** (`S1 − B1`): value = mean of the signal step - mean of the baseline step (nm); SD = the two steps' SDs added in quadrature, `sqrt(SD_S² + SD_B²)`. This is the scatter of a difference of two single cube values: it assumes independent cubes (smoothing makes neighbours alike, so it is then a little too small) and it does **not** shrink with more cubes. The uncertainty of the difference of the *means* is the SEMs in quadrature, which the SEM display shows (2026-11-06, below).
- **Signal to noise** (`(S1 − B1) / noise`): the difference divided by the noise of the baseline step, which is the SD about a straight line through the step (`step_stats.StepStats.noise`, ddof 2: a steady drift of the baseline is not counted). A pure number, no SD; NaN with fewer than three cubes or a baseline with no scatter. Shown with one decimal.
- **Derived, not calculated.** `compare_values` is arithmetic on the step numbers a row already has (`RowNumbers.value_at`; rows now also carry `noise`, taken from `LineStepValues.noise`), so a comparison column needs no calculation, changes the moment the user picks other steps for the pair in the Sensorgram's Evaluation pop-up, is empty until the pair has both steps, and is current exactly when the row's numbers are. Groups have comparison values too (of the averaged line).
- **Columns.** `StepTableModule.add_compare / set_compare_op / remove_compare / restore_compare`; `columns()` is the steps and then the comparison columns (`StepColumn.kind == "compare"`, ref `("cmp", uid)`), so the model, the sort, the widths and the export treat them like step columns. The add icon (`math-function`, after the Subtract switch) takes the next (evaluation pair that is set, operation) combination not yet shown, else pair 1 / difference; with no pair set the column is made anyway and the footer says where to set it.
- **Header.** A comparison column's header has an arrow at its left end (`SubscriptHeader`, `COLUMN_KIND_ROLE`); a click there opens the menu (the two operations with the pair's names, "Remove this column") and is not a sort click (the release is swallowed); a click elsewhere on the header sorts. The list `[[pair, operation], ...]` is remembered (`roi_table/compare_columns`) and not written before it has been read once at start-up.
- **Export.** One block per column: `S1 - B1 difference (nm)`, `S1 - B1 sd (nm)`, `S1 - B1 n`; the ratio has no SD column (in "SD only" display it keeps its value column so the table still says something); the JSON record lists the comparisons.
- **Tests.** `compare_values` and noise in `tests/unit/test_lspri_roi_table_step_columns.py` / `test_lspri_step_table.py`; module and panel in `tests/integration/test_lspri_step_table.py` (values equal the arithmetic and a numpy noise check, the pair set / unset without a new calculation, current exactly when the steps are, add order, remember and restore, the arrow and the menu with `QMenu.exec` intercepted, sort, export).

**Not built / open:** a pick for *any* S and B (the column is tied to an evaluation pair for now, as the maintainer said "later"); more operations (a ratio S/B, a relative change). A bug of mine caught by the test run: a header click on the arrow ran the real, blocking menu in a test; the test now intercepts `QMenu.exec`.

## 2026-11-06 follow-up: SEM, and frozen columns

Asked for by the maintainer: "You can add also SEM. Also, add to columns right-click menu a column freeze (always shown when scrolling), especially useful for the group column."

**SEM** (standard error of the mean, `SD / sqrt(n)`, n = the cubes of the step). Two more choices in the display picker: `SEM` and `Mean ± SEM` (keys `"sem"`, `"mean_sem"`; `"both"` is still mean ± SD, so saved state keeps working).
- *Derived, not calculated*: `step_table.sem_of(n, sd)` (NaN below two cubes); `CellValue.sem` is filled when a cell is made, so switching to SEM needs no recalculation and nothing out of date appears.
- *Comparison columns*: a difference's SEM is the two steps' SEMs in quadrature (`compare_values` now returns `(n, value, sd, sem)`); it shrinks with more cubes, the SD of the difference does not. A signal-to-noise column has no spread, so it **shows its value in every display** (before, it was empty in the SD-only display; `RoiTreeModel._mode_of`).
- *Decimals*: one number of decimals for the whole table follows the spread that is shown: the SEM in the two SEM displays (it is typically ten times smaller than the SD, so the SD's decimals would round it to nothing and the mean would be quoted more precisely than it is known), the SD otherwise (`step_columns.table_decimals(cells, mode)`).
- *Sorting* follows what is shown (SEM column: by the SEM; mean ± SEM: by the mean). *Tool tip*: always gives the SEM and its formula. *Export*: `"... sem (nm)"` where the display shows it; the JSON record says what sem is.
- **Caveat the maintainer should know**: the SEM counts every cube as an independent value. Smoothing makes neighbouring cubes alike (`step_stats` module docstring), so with smoothing on the SEM is somewhat too small. The numbers are as honest as the SD's own independence assumption; they are not corrected.

**Freeze columns.** Right-click a column header: "Freeze columns up to "<column>"" and "Unfreeze columns" (the menu that also holds the view choice). The columns from the first (on screen) up to the chosen one stay at the left edge while the table scrolls sideways.
- *Meaning*: like freeze panes in a spreadsheet, not one column alone (a column that stays while the ones before it scroll away would be cut loose from its row). Only the fixed columns (#/ROIs ... Shape) can be the last frozen one; the step columns are what scrolls. A column the freeze ends at that is hidden (the Simple view hides the geometry columns) freezes the visible ones before it.
- *The group name*: it is drawn across the columns after #/ROIs, so a freeze up to #/ROIs alone keeps a group's chevron, colour and count but little room for its name (it is cut at the frozen edge). Freezing up to the second column (Label in the Simple view, x in the Geometry view) keeps the names. The menu tip says so.
- *Too wide*: frozen columns may fill at most 60 % of the view; beyond that the freeze waits (the footer says why) and starts working when the panel is wider.
- *Remembered*: `roi_table/frozen_upto` (a column number, -1 = none).
- *How, because `QTreeView` has no frozen columns* (`panels/roi_table/view.py`, module docstring): after Qt draws a row scrolled as usual, the frozen cells are drawn again, with the same delegate, at their unscrolled places over the left of the row (`drawRow`); the header does the same with its sections (`paintEvent`). What answers "which cell is here" and "where is this cell" is shifted the same way (`indexAt`, `visualRect`, the header's mouse events and `section_at`), so clicks, tool tips, drag and drop, cell editors and the header's sort clicks land on what is drawn. With nothing frozen every override falls straight through to Qt. The delegate now measures a group header's name and step numbers from the cell's own rectangle instead of the scroll position (so the same code draws both copies) and keeps the name inside the frozen edge. `freeze.py` holds the menu entries and the saved state.
- *A trap found by the test*: Qt draws a faint frame across the whole row of the current row of a view with focus (`allColumnsShowFocus`) *after* the cells; the second drawing has to add it too, through the **application** style (the view's own style is wrapped by its stylesheet, whose `outline: none` draws nothing there). Without it the frozen part of the current row lacked the tint the rest of the row has.
- *Not handled* (small): keyboard navigation to a cell that is under the frozen columns does not scroll it clear of them; double-clicking a header section's edge to size it is not remapped while scrolled.
- **Tests**: `tests/integration/test_lspri_roi_table_freeze.py` (offscreen, real painting): which columns are held, the frozen region's pixels equal scrolled or not for the rows, group headers, the current row's frame and the header (with the control that they differ without a freeze), hit-testing, cell rectangles, the editor over a frozen cell, header clicks, the menu entries and the remembered state. SEM: `tests/unit/test_lspri_roi_table_step_columns.py`, `tests/integration/test_lspri_step_table.py`.
- **Not looked at on screen** (GUI rule): how the frozen edge line looks, the group name's cut at the edge, the feel of scrolling.

## 2026-11-06: step columns carry the colour of their step

Asked for by the maintainer: the columns of the experimental steps should have the same background as the step segments in the Sensorgram.

**What is shown.** A step column (header, ROI cells, group-header cells) is filled with the colour the Sensorgram's plan bar paints that step with, at the bar's own opacity (the slider in the bar's ribbon group, default 0.55), blended over the table's background exactly as the bar blends over the plot. Opacity 0 on the bar slider = no colour in the table. A comparison column (S1 - B1 ...) belongs to no single step and stays plain; so do the fixed columns. Selection and hover tints are painted over the fill, so a selected row still shows.
- *One colour, one source*: `plan.bar_model.effective_colors(steps, separators)` (the user's own colour, else the automatic one of the step's solution) is used by `build_bar_steps` for the bar and by `StepTableModule.columns()` for the table (`StepColumn.color` now holds the colour the bar paints, it used to hold only the user's own). The separators are the bar's (the table already followed them for the titles), because the automatic colour is chosen per *solution*, which the separators define. A colour edit already rebuilt the columns, so it reaches the table by itself.
- *The bar's opacity*: `app_rewrite._follow_plan_bar` (was `_follow_step_titles`) hands the bar's text mode, separators **and opacity** to the table, now and on every change; the opacity goes `RoiTablePanel.set_step_tint_alpha` -> `RoiTreeModel.set_step_tint_alpha` and **only repaints** (colours are read from the model while painting: `STEP_TINT_ROLE`, a `QColor` with the opacity in its alpha, for cells and headers; one colour per column made when the columns or the opacity change, not per cell). It does not depend on whether the bar is *shown* (hiding the bar does not strip the table).
- *Text colour*: dark or light by `contrast_text_color`, the function the bar uses for its labels, judged on the blended fill (`delegate.tinted_text_color`), so a number stays readable on any step colour and any opacity. An out-of-date number is the same colour, fainter (alpha 135), because `text_dim` could vanish into the colour.
- *The header is drawn by hand for a coloured step* (`SubscriptHeader._paint_tinted_section`): the header's style sheet gives every section an opaque background, and Qt ignores a header model's `BackgroundRole` once a sheet sets the section background, so a colour cannot be put under it. The hand drawing copies what the sheet gives a section (base colour, the 1 px line below, 6 px padding, semi-bold font, the model's alignment: right) — **if `panel.py`'s `QHeaderView::section` rule changes, change `_SECTION_PADDING` and this method with it.** It measured identical to the stock header (same ink box for the title) in an offscreen render.
- *Sort triangle*: drawn by hand too, small, at the left end of the section (up = ascending), so the right-aligned title does not move when a column becomes the sorted one. In an offscreen render (Fusion) the stock step headers show **no** sort arrow at all (the header's style sheet suppresses Qt's own); on the maintainer's Windows the base style is Windows', which may differ, and I could not check it. If the other headers do show an arrow there, the two looks may differ a little.
- **Not looked at on screen** (GUI rule): how strong 0.55 looks behind 160 rows of numbers (lower the bar's opacity slider if it is too loud: the table follows), the triangle, the header on a light theme.
- **Tests**: `tests/integration/test_lspri_step_tint.py` (19; real pixels offscreen: cell, group header, header section = the bar's colour blended over the background; the opacity link incl. 0; repaint-only; selection still visible; the sort triangle; readable text), `tests/unit/test_lspri_plan_bar_model.py` (`effective_colors`). A trap met while writing them: Qt paints the current row's focus highlight over its cells, so a pixel test needs no current row (`setCurrentIndex(QModelIndex())`).

## 2026-11-06: the step columns fit their content

Asked for by the maintainer: "adjust the width of the column so it matches the content". Until now every step column had one width (118 px, or whatever the user dragged them all to).

**Rule.** By default each step column is as wide as the widest of (a) its title, bold as the header draws it, plus the room for the sort triangle (or, in a comparison column, for the menu arrow), and (b) the widest thing any row shows in it: ROI rows and group headers, collapsed groups included, so opening a group never changes a width. Clamped to 56 - 360 px (a longer title is cut with "...", its tool tip has the whole note). A column with no numbers yet keeps the old 118 px, so it does not jump narrow and then wide when the first calculation ends.
- *Why per column and not one shared width*: a comparison column's signal-to-noise numbers are short, its title is long; a "Mean" display is much narrower than "Mean ± SD". One fit for all would waste the room the user wants back.
- *When it re-fits* (only while fitting, never over a width the user chose): numbers arrive or go, the display or the decimals change, a step is retitled or added or removed, a comparison column comes or goes, and at the end of every table rebuild (`RoiTablePanel._rebuild` -> `StepColumnControls.fit_if_auto`), which also catches up what changed while the dock was hidden. A hidden panel is not re-fitted.
- *Where*: the text of each row comes from `RoiTreeModel.step_texts(position)`; the width from `RoiTreeView.step_column_fit` (view = fonts and padding; `delegate.CELL_ROOM` is the padding a number needs); `step_columns.widest_text` measures only the 64 longest distinct texts of a column (the cells have one number format, so the widest is among the longest: about 60 font measurements a column instead of hundreds with 1,500 ROIs).
- *The user's own width*: dragging the edge of a step column gives **all** step columns that width (as before) and **stops the fitting**; remembered under `roi_table/step_width_manual` (None / absent = fitting). Going back: a **double-click on a step column's edge** (the spreadsheet convention) or **"Fit step columns to content"** in the header's right-click menu (shown only while a manual width exists). A double-click on a *fixed* column's edge behaves as before.
- *The old key `roi_table/step_width` is ignored.* It was written automatically (the first programmatic width change was taken for a drag), so a saved 118 never meant a choice. A width someone had really dragged to is therefore forgotten once; the columns fit instead.
- *Fitting is never mistaken for dragging*: the controls set widths under a `_resizing` guard; Qt's own fit of one column during a double-click is ignored by the panel (`SubscriptHeader.in_double_click`) and replaced by the fit of all of them (`fit_requested`). `RoiTreeView.sizeHintForColumn` answers with the fit for a step column, so even Qt's stock "resize to contents" lands on it (the delegate used to answer 0 wide, which made the old double-click shrink a column to its title). The header's double-click is also moved like the other mouse events when the table is scrolled under frozen columns (a gap listed on 2026-11-06 earlier).
- **Tests**: `tests/integration/test_lspri_step_column_width.py` (16: every cell and the title fit and the column is not much wider; mean vs mean ± SD; the title; no numbers; catch-up after hiding; nothing saved for a fit; the sort triangle clears the title of the narrowest column; comparison column's arrow room; drag; double-click on an edge and on a fixed column's edge; the menu entry; restore, incl. the old key), `tests/unit/test_lspri_roi_table_step_columns.py` (`widest_text`).
- **Measured, offscreen (Fusion), this test dataset**: titles set the width with the long default notes (101 and 122 px, instead of 118), the numbers with short titles (93 px each); "Mean" alone 56 px. Real fonts on the maintainer's Windows will differ a little.
- **Not looked at on screen**: how it feels when widths change as numbers arrive (a recalculation can widen or narrow columns), and that a very long note makes a wide column (the note style in the Sensorgram's plan bar, "Text: solution", shortens it).

## 2026-11-06: hide and show columns (header right-click)

Asked for by the maintainer: hide a column from the table's column menu, and a way back: one entry that shows all, one that lists the hidden columns.

**The menu** (right-click a column header; after the view choice, before Freeze): **Hide column "<that column>"**; **Show hidden column** (a submenu listing the hidden columns, left to right: pick one); **Show all hidden columns**. When nothing is hidden the two show entries are greyed with the tip "No column is hidden." (they stay in the menu so the user can see they exist). Hiding says in the footer how to bring the column back. #/ROIs can be hidden too, in a special way (see "Hiding #/ROIs" below).
- *Hiding is a layer on top of the view mode.* A column shows when the view mode (Simple / Geometry) has it **and** the user has not hidden it, so switching the view never brings a hidden column back. A column the user hid that the current mode does not show is **not listed** (showing it would change nothing on screen); it is listed again in the mode that has it. "Show all" clears everything, in every mode.
- *One place decides what shows*: `RoiTreeView.refresh_column_visibility` (mode columns + hidden set). `set_view_mode`, the two step-width loops (they used to un-hide every step column) and `RoiTablePanel._rebuild` (new step columns arrive visible after a model reset) all go through it. If you add anything else that shows or hides a column, use it, or a hidden column comes back.
- *Naming a column* (`column_keys.py`, pure): a fixed column by its number (0-7); a step by its plan reference (`StepRef`: measured step + start time + note, or an added step's uid) so it stays hidden when other steps are added or removed and means nothing in another experiment; a comparison column by `("cmp", pair, operation)` (its uid is renumbered at every start). Consequence, on purpose: choosing another calculation in a hidden comparison column's header makes it a different column, so it shows. Saved under `roi_table/hidden_columns` as a list (numbers, `ref_to_payload` objects, `{"compare": [pair, op]}`); entries that cannot be read, or name #/ROIs, are skipped; stale ones (a step that is gone) stay in the saved list until "Show all".
- *Side effects handled*: a table sorted by the column that is hidden goes back to the # order (as when a view mode hides it); a hidden column keeps its width (fixed: Qt remembers it; step: the fitting sets the size of hidden sections too); a freeze that ends at a hidden column holds the visible ones before it (existing rule); a group header does not draw numbers for a hidden step column (the delegate already skipped hidden columns).
- **Tests**: `tests/integration/test_lspri_roi_table_hide_columns.py` (25), `tests/unit/test_lspri_roi_table_column_keys.py` (4).
- **Not looked at on screen**: the submenu, and how the menu reads with its separators when some entries are greyed or hidden.

## 2026-11-06 (later): hiding #/ROIs, and where two modules live

**Hiding #/ROIs.** Asked for by the maintainer: the column holds nothing they evaluate, so it should be hideable; how it is done does not matter as long as the rest of the table keeps working. A plain Qt hide cannot do that: a group header is **one cell spanning the whole row that Qt attaches to the first column**, so with that column hidden Qt paints no group header at all (no chevron, name or step numbers) and there is nothing to click, rename or drop on (measured with a paint probe). So hiding #/ROIs **collapses it to zero width** and keeps it a column for Qt (`RoiTreeView.refresh_column_visibility` / `_collapse_first_column`).
- *What the user sees* (first version; the chevron, chip and count of a group header were left out afterwards, see "Follow-up" below): the group headers are unchanged; a ROI row loses its colour dot and number (the delegate skips them in a zero-width cell, else the dot would be drawn over the next column); the first visible column starts at the left edge; child rows are no longer indented (the indent was inside that column).
- *What keeps working* (each pinned by a test; the chevron click no longer does while #/ROIs is hidden, see "Follow-up"): a group is renamed with the editor in view, a click at the left edge finds the ROI row, a drop on a group header, the sort (the # order stays the default, nothing is rebuilt), a freeze up to a later column (#/ROIs adds no width), the step columns and their fitting, the saved state, and the menu (it opens from anywhere on the header; the zero-width section has no place of its own to click).
- *The section is fixed while hidden*: the left edge of the next column is also this section's drag handle, so without this it could be dragged open by accident. Width setting goes through `RoiTreeView.set_fixed_column_width`, which leaves it at zero and keeps the width for when it is shown again (the panel's `_apply_widths`, the view mode switch and the default widths all use it). Showing it restores that width and the handle.
- *Be aware*: the Simple view shows only #/ROIs and the group label, and a ROI row has no label (labels belong to groups), so with #/ROIs hidden the ROI rows of the Simple view are blank. The Geometry view and the step columns are where hiding it makes sense. A row without its number is anonymous: the ROI's identity is then only its position in the table.

**Bug found by the maintainer the same evening: with #/ROIs hidden the table went empty after any rebuild (fixed).** Symptoms: at start-up with the column hidden the rows were empty; after a click on a group (or the refresh that follows a selection) everything, group names included, vanished; showing #/ROIs again brought it all back. Cause: every row got **height 0**. The delegate answers a row's height only for column 0 (`sizeHint`, a 2026-10-07 speed shortcut: `expandAll` on 1500 ROIs 1.3 s -> 0.2 s), but Qt asks the columns **from the first one with width** on (`QTreeView::indexRowSizeHint` starts at `header->visualIndexAt(0)`), so with #/ROIs at zero width column 0 is never asked and the other columns answered "0". The table looked fine right after hiding because the old heights were cached; the first rebuild (start-up, a group click, a re-sort, a new scan) re-measured them. My first tests hid the column *after* the rows were measured and never rebuilt, which is why they passed. Fix: while `first_column_collapsed`, every column answers the height (`RoiTableDelegate.sizeHint`); the shortcut stays for the normal case. Cost of the extra check: about 1 us per `sizeHint` call (2.1 vs 1.2 us), i.e. roughly 9 ms more on a 1500-ROI rebuild (measured: rebuild 110 ms Simple / 205 ms Geometry before, within noise after). Regression tests (they fail without the fix): `test_the_rows_keep_their_height_when_the_table_is_rebuilt_with_the_column_hidden`, `test_a_click_on_a_group_header_with_the_column_hidden_does_not_empty_the_table`, `test_a_panel_started_with_the_column_hidden_has_rows`, `test_the_delegate_gives_a_row_height_from_the_first_column_with_width`. **Lesson for this table: a test of a layout change must rebuild (`refresh_now`) afterwards, and check `visualRect(...).height() > 0`, not only widths.**

**Comparison column titles are formulas (2026-11-06, maintainer: "instead of S1 and B1 write the variables, like \mu_S1 - \mu_B1 / \sigma; B1 and S1 do not always follow the setting of the other columns").** The difference column is titled `μ_S1 − μ_B1` and the signal-to-noise column `(μ_S1 − μ_B1) / σ_B1` (pair 2: `μ_S2 ...`); μ = the mean of the step that has that role, σ_B1 = the noise of the baseline step (its SD about a straight line). I wrote the noise as σ_B1, not a bare σ, and put the brackets round the difference (the maintainer's line had neither): a bare σ does not say whose, and `μ_S1 − μ_B1 / σ` would read as μ_S1 − (μ_B1 / σ).
